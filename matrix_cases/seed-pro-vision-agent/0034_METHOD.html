Rendering method (local pixel ops only)

  1. Static "clean plate": erase (a) each HSV block mask, (b) the idealised rotated w×h block footprint polygon about its base pivot (catches dark side faces the hue mask misses), (c) three contact/cast-shadow ellipses per block, and (d) the crank ellipse; dilate the union 3 px.
    • Wood holes: every erased table pixel is filled by same-row linear interpolation between the nearest clean wood pixels left and right (searchsorted), smoothed only inside the hole by a mask-normalised 15×15 Gaussian, plus synthesised horizontal grain.
    • Platform holes: top-surface pixels filled from clean photographed disk pixels on the same row (top shade is constant in x); cylinder-side pixels from the nearest clean side donor on the row. No procedural disk painting — colours come from the photo, so rim joins are exact.
  2. Each moving block: RGBA sprite cut from the original pixels against the clean plate (rim coverage by colour unmixing d_bg/(d_bg+d_fg), 0.6 px blur), rigidly rotated with cv2.warpAffine about its measured base pivot (δ=θ−θ0; positive = visual CCW = tip left). A lighter top-face quad (rotated projected box-depth vector) is added while tipping; a soft contact ellipse plus a blurred alpha-based elongated body shadow track the fall. Blocks composited back-to-front (purple first, yellow last).
  3. Rotating crank drawn before the blocks (blocks occlude it when in front): rigid radial arm + back handle bar + hub + cream peg capsule, 55°/s.

METHOD.md

METHOD — case_0034

Task: given first_frame.png (256×144, locked-off camera), generate the 20 frames (4 fps, 5 s) of a black rotating platform whose wooden stick sweeps clockwise and knocks over six coloured domino blocks in the order purple → blue → green → pink → red → yellow.

Everything is local pixel manipulation with NumPy/OpenCV in generate.py (single run, deterministic RNG seed; no network, no external models/engines, no rendering beyond 2-D image ops). Frame 00 is the source PNG byte-for-byte; frames 01–19 are 2-D composites built on top of a reconstructed "clean plate".

1. Measurement (see OBSERVATION.md)

  • HSV masks for the six block hues, each restricted to the largest connected component, morphologically closed and interior flood-filled. From each mask we derive: mean face colour, light/dark colours (luminance percentiles), width w, height h, base pivot (x, y+0.5) at the left base corner (the physical tipping axis), top-edge centre/width, and the small initial lean θ0 (−2°…+4°, measured from the mask axes).
  • The black platform is an ellipse (top centre (180,43), semi-axes (45.5,16.4)) with a cylindrical side (bottom centre (180,66.5)). The wall/table seam is a measured line, y = 57 − 0.108·x.
  • The crank is a rigid assembly rotating on the disk: pivot (187,40), projected orbit semi-axes (23,10), frame-0 azimuth α0 = 15° (peg at (181,50), already touching purple), angular speed 55°/s clockwise from above (the near-side peg moves screen-left).

2. Clean-plate reconstruction

A single static background image (no blocks, no crank) is built once.

Erase mask (all dilated 3 px for anti-aliased fringe coverage):

  1. the six HSV block masks;
  2. for each block, the idealised rotated w×h footprint polygon about its pivot at θ0 — this catches the very dark side strips the hue masks miss;
  3. three soft contact/cast-shadow ellipses per block (all block shadows are re-rendered per frame);
  4. an ellipse over the original crank pixels.

Wood fill (erased pixels on the table): wood grain is horizontal, so every erased table pixel is filled by linear interpolation in x between the nearest clean wood pixels on its own row (found with searchsorted; rows without donors borrow the nearest row that has them). The result is smoothed only inside the erased region using a mask-normalised 15×15 Gaussian blur, then given synthesised grain (two horizontal Gaussian noise fields with the large-scale DC removed). Dark platform pixels can never streak into the wood because donors are restricted to clean table pixels.

Platform fill: holes on the disk top are filled from clean photographed disk pixels on the same row (the top shading is constant along a row → linear interpolation), and holes on the cylinder side from the nearest clean side donor on the row. Because every replacement colour is sampled from the real disk at the same y, the joins at erase boundaries are exact and the real rim/specular features are preserved.

(Note: cv2.distanceTransformWithLabels(..., DIST_LABEL_PIXEL) is broken in OpenCV 4.x — it labels connected components rather than pixels — so the donor lookups are implemented explicitly.)

3. Moving objects

Block sprites. Each block is cut from the source as an RGBA sprite. The colour mask gives interior alpha 1; the 1-px dilated fringe gets soft coverage by colour unmixing against the clean plate, α = d_bg / (d_bg + d_fg), followed by a 0.6-px Gaussian. Per frame the sprite is rigidly rotated about its pivot by δ = θ−θ0 with cv2.getRotationMatrix2D/warpAffine (positive δ = visual CCW = tips left). While tipping, a lighter "top face" quad is added: the rotated top edge extruded by the rotated projected box-depth vector (2–4.6 px), so the 3-D box top opens up as it falls. At θ = 90° blocks lie flat pointing left from their pivots (the front blocks then run off the left edge of frame, as the measured spacing implies).

Shadows, all table-clipped and multiplied into the canvas at 0.5: a compact contact ellipse that fades with 1 − sin θ, a faint rear cast ellipse, and — past 6° — the rotated sprite alpha itself, blurred 2.4 px, offset (4,−1) toward the light, as an elongated body shadow.

Keyframed angles (ANG in generate.py): per-block screen angles at all 20 frames, hand-timed to the physical chain — purple starts at frame 1, each successive block starts ~0.5 s later (peg pushes purple first; contact gaps from the measured 19–26 px pivot spacing correspond to ~19–26° arcs), purple is flat by frame 6, yellow (last) by frame 12; all blocks then rest flat through frame 19.

Crank, drawn each frame at α = 15° + 55°·t/4: a dark radial arm from pivot to peg, a 31-px dark perpendicular handle bar mounted behind the pivot (r = −0.55, so it sits on the opposite side of the orbit), a small hub, and the cream wooden peg capsule (RGB ≈ (183,155,129)) oriented along the radius with a 1-px highlight. It is composited before the blocks, so standing blocks occlude it correctly.

Compositing order per frame (01–19): plate → all six block shadows (multiplicative) → crank → blocks back-to-front (purple … yellow) with their top-face quads.

4. Outputs and verification

artifact_io.save writes pixels.npz (the (144,256,20) uint32 0xRRGGBB tensor), frames/00.png…19.png, inspection.png (frames 0,2,5,8,11,14,17,19) and the index.html player; generate.py also writes transition_check.png (128×72 thumbnails plus per-step absolute- difference heatmaps for all 19 transitions).

Verified:

  • frames/00.png is pixel-identical to first_frame.png;
  • every PNG is bit-identical to its pixels.npz tensor slice;
  • visual review of enlarged key frames and the transition heatmaps shows a continuous cascade with no teleport jumps or stray ghosts;
  • an assertion checks every erased pixel classifies as wood or platform (no wall contamination).

Known simplifications

  • The crank is a traced/geometric approximation (the real linkage is a few dark pixels; two bars + peg read correctly at this resolution).
  • Blocks are rigid sprites with a single added top-face polygon; no per-pixel physical deformation, and the depth-order overlap of fallen blocks is a flat painterly stack.
  • Wood texture inside the original block footprint is reconstructed, not recovered; shadows are stylised ellipses/alpha blobs rather than a photometric solution.
