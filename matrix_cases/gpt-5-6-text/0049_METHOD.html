Actual generation method

This sequence was generated entirely with local Python numeric pixel operations. No image viewing/reading tool, external model, network resource, external engine, mask, or reference image was used.

  1. first_frame.png was loaded as a 256 x 144 uint8 RGB array with Pillow.
  2. Scene geometry was measured numerically from RGB/luminance thresholds, connected components, row runs, and coordinate samples. Those measurements and the event schedule were written to OBSERVATION.md before generate.py was created.
  3. Six domino silhouettes and their table-contact pivots were represented with hand-measured polygon masks. The photographed pixels inside each polygon are retained as the object's texture.
  4. A single static clean plate was made locally with OpenCV TELEA inpainting over the measured moving-object masks. A small amount of shifted high-frequency source texture was mixed into only the reconstructed pixels so the table cleanup did not become unnaturally smooth.
  5. Each domino is rotated as a rigid textured sprite about its measured lower contact edge. Cubic RGB resampling and linear alpha resampling provide subpixel motion. The sequence is staggered from the upper-right to lower-left, with smoothstep angular easing and slight perspective foreshortening near horizontal.
  6. The source pixels of the dark stained-wood arm are rotated clockwise about the mount pin. The fixed black mount is copied back from the source after arm cleanup. A small pin cap and restrained blurred contact shadows make the attachment and table contact legible.
  7. Every later frame starts as a copy of frame 00. Reconstructed background is revealed only beneath an object once that object has begun moving; all untouched areas remain copied directly from the supplied source.
  8. artifact_io.save writes the uint32 packed 0xRRGGBB tensor, individual lossless PNG frames, the inspection sheet, and the standalone HTML player. generate.py separately creates transition_check.png from selected frames and amplified numeric adjacent-frame RGB differences.

Timing

  • Resolution: 256 x 144 RGB
  • Frame count: 20
  • Playback rate: 4 fps
  • Nominal duration: 5 seconds
  • Frame 00: exact RGB-array copy of first_frame.png
  • Motion: clockwise arm sweep, followed by an eased six-piece domino cascade and final settling

Verification performed

generate.py verifies all of the following after saving:

  • array shape is exactly (20, 144, 256, 3) and dtype is uint8;
  • frame 00 is exactly equal to the supplied source array;
  • all 20 PNG files round-trip to exactly the generated arrays;
  • pixels.npz contains a (144, 256, 20) uint32 tensor;
  • every tensor value exactly matches the corresponding PNG's packed 0xRRGGBB pixel;
  • every adjacent pair contains a nonzero transition.

An additional numeric-only audit measured the transition bounding boxes. They progress from approximately x=169--211, y=14--34 at the initial arm motion to x=49--81, y=87--106 at final settling, matching the intended upper-right-to-lower-left cascade. No claim of visual review is made.
