magnet-wrench · 生成方法

Source inspection

I did not use an image Read/View tool. I loaded first_frame.png locally with Pillow/OpenCV and inspected only numeric RGB summaries, perceptual color clusters, grayscale/edge maps, connected-component statistics, contour coordinates, and text/ASCII renderings derived from those values.

That inspection located the black platform at roughly x=108..199, y=43..101, the magnet assembly to its left, and the small steel wrench at x=103..115, y=51..71. A Canny contour around the wrench measured about 13 x 21 pixels, with its rotation center set to (109.5, 61.0).

Pixel generation

generate.py performs the animation deterministically:

  1. It forms a tight geometric support around the measured wrench.
  2. Inside that support, it separates the cool/bright steel pixels from the warm table and charcoal platform by luminance and blue-minus-red chroma. The largest connected component is retained, lightly closed, and given a 0.42-pixel soft edge.
  3. It dilates that matte only for background reconstruction and uses OpenCV Navier-Stokes inpainting with a 3-pixel radius to restore the tiny stationary wrench footprint. This reconstructed plate is used only from frame 01 onward; frame 00 is copied byte-for-byte from the source.
  4. It rotates the source wrench pixels clockwise around (109.5, 61.0) using bicubic resampling. The angle follows cubic smoothstep, 148 * (3u^2 - 2u^3) degrees for u = frame/19, producing gentle onset, sustained clockwise motion, and a settling finish without reversal.
  5. A faint blurred contact shadow, offset about (1.0, 1.25) pixels, rotates with the wrench to keep it grounded. The camera, magnet, table, platform, lighting, and all pixels outside the local action area remain fixed.

Packaging and checks

The shared artifact_io.save helper writes the 20 RGB PNGs, packed uint32 pixels.npz, inspection sheet, and standalone HTML player. generate.py additionally writes transition_check.png as before/after/difference rows for five temporal transitions.

Automated checks confirm:

  • 20 frames, each RGB uint8 and 256 x 144;
  • frames/00.png and the in-memory frame 00 exactly equal first_frame.png;
  • every PNG exactly matches its corresponding generated RGB frame;
  • pixels.npz has uint32 shape (144, 256, 20) and every packed 0xRRGGBB value matches the PNG tensor;
  • changes are confined to a conservative wrench region x=94..124, y=44..77, with zero changed pixels elsewhere;
  • the clockwise angle is monotonic from 0 to 148 degrees.

The method is entirely local and uses no network resources, external models, external engines, masks, other cases, or subagents.
